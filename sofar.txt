ROOT CAUSE OF THE "DROPS OFF THE NETWORK" SYMPTOM (confirmed, same on both Pis)
- It is a marginal Gigabit Ethernet link between this PC's Intel I219-LM port/cable and the
  Pi 5's onboard NIC (driver "macb", PHY "Broadcom BCM54213PE").
- Kernel log pattern seen on BOTH Pis at boot:
    Link is Up - 1Gbps/Full   (negotiates gigabit)
    Link is Down              (drops almost immediately - this is the "Pi disappears" symptom)
    Link is Up - 100Mbps/Full - flow control off   (falls back, then stays stable)
- Once it settles at 100 Mbps the link does NOT flap again. The failure is specifically the
  1000BASE-T autonegotiation/training on this cable/port combination, not Wi-Fi, not power,
  not Docker, not netplan IP config (alpha-p's netplan has no explicit speed override; its
  stability comes from the dispatcher script below).

THE ACTUAL FIX, FOUND ON alpha-p (PAMS Pi)
- File: /etc/NetworkManager/dispatcher.d/50-eth0-stable  (root:root, mode 755)
    #!/bin/sh
    IFACE="$1"; ACTION="$2"
    [ "$IFACE" = "eth0" ] || exit 0
    case "$ACTION" in
      up|hostname|dhcp4-change|connectivity-change)
        /usr/sbin/ethtool -s eth0 autoneg on advertise 0x008 2>/dev/null || \
          /usr/sbin/ethtool -s eth0 speed 100 duplex full autoneg off 2>/dev/null
        /usr/sbin/ethtool --set-eee eth0 eee off 2>/dev/null
        ;;
    esac
    exit 0
  - advertise 0x008 = only offer "100baseT Full" during autonegotiation, so the PHY never
    tries (and fails) at 1000baseT. Falls back to a hard speed/duplex force if advertise
    isn't supported. Also disables Energy-Efficient-Ethernet (EEE), another known cause of
    link micro-drops on marginal cabling.
  - Confirmed on alpha-p right now: /sys/class/net/eth0/speed = 100, duplex = full, and it
    has been stable since boot (12+ minutes, no further flaps in dmesg/journalctl).

SCOPE DECISIONS (confirmed with user via ask_user before starting)
- Function: BOTH BACnet routing-style bridging AND Modbus RTU -> BACnet point mapping,
  in one service.
- Reuse PAMS's proven BACnet code/techniques as a starting point: YES.

  pymodbus for Modbus RTU) - matches the proven PAMS pattern.

IMPORTANT ENGINEERING CALL - "GATEWAY" NOT A TRUE TRANSPARENT "ROUTER"
- True BACnet network-layer routing (forwarding arbitrary NPDUs between a BACnet/IP
  network and an MS/TP network per BACnet Annex H, with foreign-device/BVLC handling)
  would mean implementing MS/TP's token-passing + NPDU routing state machine in pure
  Python. configured.txt itself explains why that is a bad idea: MS/TP has strict serial
  timing that Python's GIL/scheduler jitter cannot reliably meet (this is exactly why
  PAMS uses the compiled bacnet-stack C CLI tools for MS/TP instead of bacpypes' own
  MS/TP implementation).
- So predator's gateway instead polls MS/TP and Modbus RTU points (via the proven C
  CLI tools / pymodbus) and re-publishes them as BACnet objects on ONE local BACnet/IP
  "virtual device" that any BACnet/IP client can browse/read/write. Writes to mapped
  writable points are forwarded back down to the real MS/TP object or Modbus register.
  This is the standard "protocol gateway" pattern (as opposed to a "router") and is
  what's realistically buildable/reliable here.

       a transient under-voltage flag, e.g. 0x50005, before it clears)
   - If it starts answering ping again on its own (no replug), that is a software link-
     renegotiation issue after all.
   - If it truly stays dead until the cable is physically reseated, that points to a
     physical-layer or power issue that ethtool/dispatcher settings cannot fix - next
     would be swapping the cable, trying a different PC port, and watching the red LED
     through a drop.
3. Only re-copy the dispatcher script if step 1 shows it is missing, different, or not
   executable.

CHAPTER 8 - THE REAL DOMINANT CAUSE: eth0 WAS SET TO DHCP ON A LINK WITH NO DHCP SERVER
=========================================================================================

THE CLUE
- User sent a phone photo of predator's own monitor (direct, not VNC) showing a repeating
  desktop toast: "Requesting an ethernet network address for 'netplan-eth0' ... IP:
  192.168.1.50" - and said it "keeps flashing this". A toast like that reappearing means
  NetworkManager itself was repeatedly re-running IP configuration, not just a one-off PHY
  blip.

ROOT CAUSE (confirmed from journalctl -u NetworkManager over the full boot)
- `device (eth0): state change: ip-config -> failed (reason 'ip-config-unavailable')`
  was repeating like clockwork every ~45 seconds continuously, independent of the actual
  cable state (NetworkManager's default DHCP timeout is 45s - exact match).
- `nmcli connection show netplan-eth0` showed `ipv4.method: auto` (DHCP) with
  `ipv4.addresses: 192.168.1.50/24` only as an ADDITIONAL address layered on top - i.e.
  the connection's PRIMARY method was DHCP. predator's Ethernet is a direct point-to-point
  cable to this PC with no DHCP server, so every ~45s NetworkManager: tried DHCP, timed
  out, tore the whole connection down ("Activation: failed", state -> disconnected), then
  autoconnect kicked in and it retried from scratch - repeating forever. The static
  192.168.1.50 address only "stuck" during the brief windows between failures, which is
  why ping/SSH worked intermittently rather than being reliably either up or down.
- This is DIFFERENT FROM and MORE IMPACTFUL THAN the Chapter 4/7 gigabit-autonegotiation
  issue: that one caused occasional 1-3 second PHY-level blips (now kept at 100Mb/Full by
  Chapter 7's eth0-stable-watch.service); THIS one caused the multi-minute-long outages,
  because the IP layer never stayed "activated" long enough between DHCP-timeout cycles.
- Where it came from: /etc/netplan/90-NM-75a1216a-...yaml (confirmed via sudo cat) has
  `dhcp4: true` plus the static address only as an NM "passthrough" extra. NOTE: on this
  Pi image, files under /etc/netplan/90-NM-*.yaml are NetworkManager's AUTO-GENERATED
  REFLECTION of its own connection profiles (for `netplan status` introspection), not a
  source file - editing them directly would not stick. The actual fix has to go through
  the live NetworkManager connection (nmcli), which NM then re-renders back into that
  yaml and also persists for the next boot.

FIX APPLIED AND VERIFIED
   sudo nmcli connection modify netplan-eth0 ipv4.method manual \
     ipv4.addresses 192.168.1.50/24 ipv6.method link-local
   sudo nmcli connection up netplan-eth0
- Result: `ipv4.method: manual` now (no DHCP attempted at all). Journal shows a single
  clean transition prepare -> config -> ip-config -> ip-check -> secondaries -> activated
  in under 0.2 seconds, "Activation: successful, device activated." `nmcli device show
  eth0` -> GENERAL.STATE: 100 (connected), held stable afterward with no further
  "ip-config -> failed" entries.
- This should be the fix that actually stops the "every 5-10 minutes" symptom; Chapter 7's
  watcher service remains in place to keep the PHY itself from drifting back to unstable
  gigabit on top of this.
- NOT YET DONE: has not been watched over a long (hours) unattended period. If it still
  drops after this, check `journalctl -u NetworkManager -f` live and look for a DIFFERENT
  state-change reason than 'ip-config-unavailable' (would point to a third, separate
  cause) versus the same reason recurring (would mean this fix did not fully take/persist
  - re-check `nmcli connection show netplan-eth0 | grep ipv4.method` first).


CHAPTER 9 - GATEWAY SOFTWARE: AUTO-DETECT + CSV + GUI VIEWER + API (2026-11-05)
=================================================================================

NEW SCOPE, CONFIRMED BY USER
- Gateway must run entirely ON the Pi (not the PC): plug comms into the RJ45 (BACnet/IP)
  or the USB-C-to-RS485 adapter (BACnet MS/TP or Modbus RTU), power the Pi on, and it
  figures out the protocol and baud rate itself - no telling it what's plugged in.
- Everything found gets written to a CSV, visible on the Pi's own GUI over VNC, and
  downloadable to the PC.

WHAT WAS BUILT (all local source so far - see gateway/, scripts/, systemd/, config/,
README.md; nothing deployed to the Pi yet)
- gateway/discovery.py: the auto-detect engine. Enumerates /dev/ttyUSB*/ttyACM*; per
  port, tries BACnet MS/TP first across a baud sweep (Who-Is via bacnet-stack's bacwi -
  reuses/extends mstp.py's existing bus_scan() logic rather than hand-rolling MS/TP frame
  sniffing), then Modbus RTU (active register-read probes across a unit-id sweep, quick
  pass first then a deeper 1..247 sweep if nothing common answers) if nothing answered as
  MS/TP. Confirmed ports get a cheap periodic re-check so a swapped cable/adapter is
  noticed without a restart.
- gateway/runtime_state.py: thread-safe shared state (discovered serial ports incl.
  protocol/baud/devices, discovered BACnet/IP devices, live points-map values) - the
  single source of truth the poller/CSV/API all read, instead of the static config file.
- gateway/mstp.py: refactored to accept iface/baud overrides (was hardcoded to the one
  configured port) so discovery.py can probe any port, not just a fixed one.
- gateway/modbus_rtu.py: added probe_port() - a throwaway-client single-read probe for
  auto-detection, separate from the shared cached client used for real polling.
- gateway/csv_export.py: builds the discovered-points CSV (serial finds + BACnet/IP
  finds + curated points-map live values) and atomically writes it to [csv] path, mirrored
  to [csv] desktop_copy (~/Desktop by default) for VNC/GUI visibility.
- gateway/viewer.py: a small Tkinter window (ttk.Treeview table, re-reads the CSV every
  few seconds) so the discovered points are visible on the Pi's desktop without needing
  any spreadsheet app installed (standard Raspberry Pi OS Desktop doesn't ship one).
  Autostarts on login via systemd/predator-viewer.desktop.in -> ~/.config/autostart/.
- gateway/api.py: stdlib-only HTTP server on :8099 - GET /status (JSON), /points.json,
  /export.csv (download - this is "get the CSV onto the PC": browse to
  http://<predator-ip>:8099/export.csv or `curl -O`), POST /rescan.
- gateway/service.py: the systemd entrypoint wiring discovery + BACnet/IP + the points
  poller + csv export + the API together, with signal handling for clean shutdown.

IMPORTANT CORRECTION DURING THIS WORK: classic bacpypes DOES NOT WORK ON THIS PI
- Chapter 5 said bacpypes' BIPSimpleApplication/ReadWritePropertyServices had been
  "verified against the installed bacpypes API" - that verification was about the
  shape of the API, not about whether it actually runs on the target Python version.
- Caught by actually installing it locally (not assumed): classic `bacpypes` imports
  Python's `asyncore`/`asynchat` modules, which were REMOVED in Python 3.12. predator
  is Debian trixie (Python 3.13) / at minimum 3.12+, so classic bacpypes cannot even be
  imported there, let alone run. This would have been a dead end discovered only after
  deploying to the Pi if not caught now.
- FIX: switched to `bacpypes3` (the actively maintained asyncio-based rewrite). Rewrote
  gateway/bacnet_ip.py against it. Every non-obvious bit of its API used here was
  verified live in a local throwaway venv before writing the final code, not assumed:
    - Application.from_args() (via SimpleArgumentParser) is the correct/robust way to
      build the app - it sets up the NetworkPortObject + actual BACnet/IP UDP link layer;
      manually constructing Application.from_object_list() does NOT set up networking.
    - --address format confirmed as "<bind-ip>/<prefix>:<port>", e.g. "0.0.0.0/24:47808".
    - Vendor id: any non-default vendor id CRASHES from_args() unless that vendor's
      object/property classes are also fully registered (hit this directly: "AttributeError:
      'str' object has no attribute 'items'" deep inside bacpypes3's own object.py). Fixed
      by defaulting [bacnet_ip] vendor_id to 999 - ASHRAE's reserved id for exactly this
      (custom/unregistered device) - instead of the arbitrary 15 Chapter 5 had picked.
    - Application.from_args()/who_is()/do_WritePropertyRequest all require/are coroutines -
      confirmed "RuntimeError: no running event loop" when called outside asyncio.run().
      So gateway/bacnet_ip.py's whole flow runs in ONE dedicated thread via asyncio.run(),
      not the blocking bacpypes.core.run() pattern Chapter 5 assumed.
    - who_is() returns the I-Am responses directly as a plain list (confirmed by awaiting
      it live) - no separate do_IAmRequest handler override needed for discovery.
    - Local objects are keyed by a bacpypes3.primitivedata.ObjectIdentifier instance, NOT
      a plain (type, instance) tuple - confirmed a bare-tuple lookup silently returns None;
      every get_object_id() call here wraps with ObjectIdentifier(...).
    - do_WritePropertyRequest override uses instance monkey-patching (capturing the
      original bound method, since from_args() returns a plain Application, not a
      subclass) - confirmed this calling pattern works live.
  Because the points-poller runs on a different thread than bacnet_ip's asyncio loop,
  value updates go through loop.call_soon_threadsafe() (see gateway/service.py) rather
  than touching bacpypes3 objects directly from another thread.
