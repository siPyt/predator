ROOT CAUSE OF THE "DROPS OFF THE NETWORK" SYMPTOM (confirmed, same on both Pis)
- It is a marginal Gigabit Ethernet link between this PC's Intel I219-LM port/cable and the
  Pi 5's onboard NIC (driver "macb", PHY "Broadcom BCM54213PE").
- Kernel log pattern seen on BOTH Pis at boot:
    Link is Up - 1Gbps/Full   (negotiates gigabit)
    Link is Down              (drops almost immediately - this is the "Pi disappears" symptom)
    Link is Up - 100Mbps/Full - flow control off   (falls back, then stays stable)
- Once it settles at 100 Mbps the link does NOT flap again. The failure is specifically the
  1000BASE-T autonegotiation/training on this cable/port combination, not Wi-Fi, not power,
  not Docker, not netplan IP config (alpha-p's netplan has no explicit speed override; its
  stability comes from the dispatcher script below).

THE ACTUAL FIX, FOUND ON alpha-p (PAMS Pi)
- File: /etc/NetworkManager/dispatcher.d/50-eth0-stable  (root:root, mode 755)
    #!/bin/sh
    IFACE="$1"; ACTION="$2"
    [ "$IFACE" = "eth0" ] || exit 0
    case "$ACTION" in
      up|hostname|dhcp4-change|connectivity-change)
        /usr/sbin/ethtool -s eth0 autoneg on advertise 0x008 2>/dev/null || \
          /usr/sbin/ethtool -s eth0 speed 100 duplex full autoneg off 2>/dev/null
        /usr/sbin/ethtool --set-eee eth0 eee off 2>/dev/null
        ;;
    esac
    exit 0
  - advertise 0x008 = only offer "100baseT Full" during autonegotiation, so the PHY never
    tries (and fails) at 1000baseT. Falls back to a hard speed/duplex force if advertise
    isn't supported. Also disables Energy-Efficient-Ethernet (EEE), another known cause of
    link micro-drops on marginal cabling.
  - Confirmed on alpha-p right now: /sys/class/net/eth0/speed = 100, duplex = full, and it
    has been stable since boot (12+ minutes, no further flaps in dmesg/journalctl).

SCOPE DECISIONS (confirmed with user via ask_user before starting)

IMPORTANT ENGINEERING CALL - "GATEWAY" NOT A TRUE TRANSPARENT "ROUTER"
- True BACnet network-layer routing (forwarding arbitrary NPDUs between a BACnet/IP
  network and an MS/TP network per BACnet Annex H, with foreign-device/BVLC handling)
  would mean implementing MS/TP's token-passing + NPDU routing state machine in pure
  Python. configured.txt itself explains why that is a bad idea: MS/TP has strict serial
  timing that Python's GIL/scheduler jitter cannot reliably meet (this is exactly why
  PAMS uses the compiled bacnet-stack C CLI tools for MS/TP instead of bacpypes' own
  MS/TP implementation).
- So predator's gateway instead polls MS/TP and Modbus RTU points (via the proven C
  CLI tools / pymodbus) and re-publishes them as BACnet objects on ONE local BACnet/IP
  "virtual device" that any BACnet/IP client can browse/read/write. Writes to mapped
  writable points are forwarded back down to the real MS/TP object or Modbus register.
  This is the standard "protocol gateway" pattern (as opposed to a "router") and is
  what's realistically buildable/reliable here.
